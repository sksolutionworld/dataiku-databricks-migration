Implementation requirements

A. Acquisition

Implement or verify an acquisition service that:

1. Uses dataikuapi.DSSClient.
2. Reads connection values from CLI arguments or environment variables.
3. Downloads the complete project export ZIP.
4. Calls the Dataiku API to list every project recipe.
5. Fetches each recipe’s complete settings/configuration.
6. Captures recipe inputs, outputs, type, payload, processors, code, metadata, and dependencies when available.
7. Saves files under:

projects/<project-key>/dataiku/
├── raw/
│   ├── project-export.zip
│   ├── project_export/
│   ├── recipe_details/
│   │   ├── <recipe-id>.json
│   │   └── ...
│   └── acquisition-manifest.json

The acquisition manifest must include:
- project key
- Dataiku host, without credentials
- acquisition timestamp
- source endpoint or acquisition method
- file names
- file sizes
- SHA-256 checksums
- recipe count
- acquisition status
- framework version

Use bounded retries for transient failures. Authentication, authorization, certificate, and invalid-project failures must fail immediately with helpful messages.

Write downloads atomically using temporary files followed by rename.

If acquisition is repeated:
- default behavior: reuse valid immutable evidence when checksums pass
- --refresh: create a new timestamped acquisition snapshot
- never silently replace previous evidence
