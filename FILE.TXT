Task: Create a Standalone Databricks Migration Quality Gateway

Act as a Principal Python Architect, Azure Databricks Engineer, DevOps Engineer, and Multi-Agent Systems Architect.

Objective

Create a new standalone repository named:

databricks-migration-quality-gateway

This repository will provide an independent quality-control and handoff layer between two existing working repositories:

1. dataiku-databricks-migration — generates Databricks notebooks, Python libraries, jobs, and Asset Bundles.
2. Our existing Databricks GitHub Actions pipeline repository — deploys Databricks bundles.

Do not modify either existing repository.

Architecture

Design two cooperating components.

Agent 1: Code Review Agent

This is the primary agent.

Responsibilities:

* Inspect generated Databricks project bundles.
* Validate Python code, imports, dependencies, and file structure.
* Validate Databricks bundle configuration.
* Check generated job/task DAG consistency.
* Detect unresolved conversion markers and unsupported transformations.
* Check for exposed credentials and unsafe configuration.
* Check compatibility with the destination pipeline repository.
* Produce actionable findings with severity levels.
* Propose safe corrections.
* Require approval for changes affecting business logic.
* Revalidate after approved corrections.
* Produce a structured review report.
* Authorize handoff only when all mandatory gates pass.

Use deterministic validators for objective checks. AI assistance may be used for diagnosis and proposed fixes but must not override validation gates.

Agent 2: Code Transfer Sub-Agent

This component is invoked only after Code Review Agent approval.

Responsibilities:

* Verify the review approval and artifact identity.
* Validate source and destination paths.
* Confirm the destination is the expected local Git repository.
* Detect naming conflicts and existing changes.
* Transfer only approved artifacts.
* Preserve bundle structure and relative paths.
* Verify checksums and transferred file integrity.
* Prevent accidental overwrites.
* Produce a handoff manifest and report.
* Roll back its own changes if transfer fails.

Never bypass the review gate.

Do not commit, push, deploy, or execute Databricks jobs.

Stage 3 — Correction Planning and Offline Quality Gateway

You are working in the existing databricks-migration-quality-gateway repository.

Objective

Extend the existing Code Review Agent and Code Transfer Sub-Agent to support Stage 3: intelligent, controlled correction planning for Databricks bundles generated by our Dataiku-to-Databricks Migration Agent.

Do not rebuild or redesign the existing architecture.

The gateway must remain independent of the Migration Agent and the Databricks pipeline repository.

Our intended workflow is:

Dataiku-to-Databricks Migration Agent
→ Generated Databricks Bundle
→ Code Review Agent
→ Deterministic Quality Checks
→ Correction Proposals
→ Human Review and Approval
→ Future Controlled Corrections
→ Quality Gate
→ Future Local Pipeline Repository Transfer

Important: Stage 3 is proposal-only. Do not implement corrections or transfer bundles yet.

Stage 1 and Stage 2 are already completed.

Preserve all existing functionality unless a change is explicitly required below.

2. Databricks CLI and Workspace Access — Explicitly Out of Scope

Databricks CLI validation and Databricks workspace connectivity will be handled manually by the user.

The gateway must never execute:

* databricks auth login
* databricks bundle validate
* databricks bundle deploy
* databricks bundle run
* Any other Databricks CLI command requiring workspace interaction.

Do not connect to Databricks APIs, query Unity Catalog, or inspect live workspace permissions.

The gateway must operate entirely offline.

Update the existing BND-010 check so that:

* CLI validation is classified as MANUAL_VALIDATION_REQUIRED.
* It is excluded from mandatory offline quality-gate pass/fail calculations.
* It is clearly displayed in the final review report.
* It does not block an otherwise authorized local repository transfer.
* The gateway never claims that a bundle has been validated or deployed in Databricks.

Keep all other applicable mandatory checks enforced.

Do not weaken security, code-quality, or approval requirements.

Update the relevant policies, documentation, reporting contracts and tests consistently.

4. Correction Classification

Classify every finding into one of the following categories:

SAFE_MECHANICAL_FIX

Examples:

* Python formatting.
* Missing docstrings.
* Safe import organization.
* Replacing repeated literals with constants where behavior is preserved.
* Notebook filename normalization with complete reference updates.

CONFIGURATION_REQUIRED

Examples:

* Missing dev or personal bundle targets.
* Missing job_viewers_group.
* Missing or incompatible pipeline configuration.
* Unresolved environment variables.
* Catalog and schema configuration.

BUSINESS_LOGIC_REVIEW

Examples:

* Complex PySpark transformations.
* withColumn or filter refactoring.
* Unresolved REQUIRES_REVIEW conversion markers.
* Potential changes to joins, filters, aggregations, calculations or output schemas.

SECURITY_REVIEW

Examples:

* Model archives containing training data.
* Pickled model files.
* Subprocess usage.
* Potential secret exposure.
* Unapproved runtime dependencies.

ENVIRONMENT_VERIFICATION

Examples:

* Production catalog references in UAT.
* Runtime package availability.
* Databricks CLI validation.
* Unity Catalog permissions and table availability.

A finding may have a primary category and additional risk tags.

Do not assume a mechanical-looking change is safe unless its behavior-preserving nature can be demonstrated.
